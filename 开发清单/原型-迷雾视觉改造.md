## 一、已核实的现状（不要凭印象改）

### `_draw()` 的实际实现（`fog_of_war.gd:195-207`）

```gdscript
for gy in _rows:
    for gx in _cols:
        match _cells[gy * _cols + gx]:
            STATE_UNKNOWN:
                draw_rect(整格, Color(0.02, 0.03, 0.04, 0.97))
            STATE_EXPLORED:
                draw_rect(整格, Color(0, 0, 0, 0.45))
            _:
                pass  # 当前可见：不画
```

**只有纯色矩形。没有渐变、没有 alpha 插值、没有圆形遮罩。**

### 重绘时机（一个有利的事实）

```gdscript
func _process(_delta):
    if _dirty:
        _dirty = false
        queue_redraw()
```

`_dirty` 每 0.15 秒 tick 才置 true，**不是每帧全量重绘**。
这意味着视觉改造的性能压力比"每帧 6600 次"要小得多——
实际是**每秒约 6.7 次重绘**。

⚠️ 但 `_draw()` 内部的循环仍会在每次重绘时跑全部格子（988 格），
所以视觉细化的成本主要在 `_draw()` 内部，而不是重绘频率。

## 二、为什么「只细分」是错的（我原方案的漏洞）

评审说得完全正确。假设逻辑格是「未探索」，拆成 8px 小格后：

```
64px 逻辑格（未探索）
┌─────────────────┐
│ ■ ■ ■ ■ ■ ■ ■ ■ │  ← 8 个 8px 小格，全部继承"未探索"
│ ■ ■ ■ ■ ■ ■ ■ ■ │     画出来仍然是 64×64 的大方块
│ ■ ■ ■ ■ ■ ■ ■ ■ │
│ ■ ■ ■ ■ ■ ■ ■ ■ │
└─────────────────┘
```

**只是从"1 个大方块"变成"8×8 个小方块"，边缘依然是笔直阶梯。**

### 正确的做法：必须有「连续距离信息」

柔化的本质是：**让 alpha 在边界处连续变化，而不是二值跳变。**

这需要一份**当前不存在的**数据：
> 每个采样点到最近可见/不可见边界的距离

有两种获取方式：

| 方式 | 做法 | 代价 |
|---|---|---|
| **A. 边缘距离场** | 遮挡判定时额外记录「命中点到格心的距离」，存进一个额外数组 | 判定层要改（但不影响存档） |
| **B. 绘制时插值** | 不存数据，绘制时对边界格做 `smoothstep` 过渡 | 纯视觉层改动，判定不动 |

**建议先试 B**——因为它符合"判定层不因视觉而改"的原则。
若 B 的效果不够（比如复杂墙角仍然生硬），再考虑 A。

### B 的具体思路

```
判定结果不变（64px 三态）
绘制时，对处于「状态边界」的格子做特殊处理：

  格子完全在可见区  → 不画（现状）
  格子完全在未知区  → 画 0.97（现状）
  格子跨越边界      → 按「可见部分占比」画 0.97 * 占比
                    → 或切成几个小条带，每条 alpha 不同
```

这样至少能让**边界格**从"整格跳变"变成"部分覆盖"，
阶梯感会明显减轻，但不会完全消失。

## 三、本轮只做原型验证（不全面替换）

### 目标

**不是**做出最终效果，而是**验证这条路可行不可行**。

### 具体做法

**Step 1｜加一个调试开关**

```gdscript
@export var visual_mode := 0   # 0 = 现状, 1 = 柔化, 2 = 柔化+轻微噪声
```

用一个键（如 `F6`）在三种模式间切换，方便同场景对比。

**Step 2｜只改 `_draw()`**

- `visual_mode == 0`：走现有逻辑（作为基线）
- `visual_mode == 1`：实现边界格插值（方案 B 的简化版）
- `visual_mode == 2`：在 1 的基础上叠 4~8px 噪声（**本轮可不做**）

**不动**：判定逻辑、存档格式、地图画布、`_cells` 数组结构。

### Step 3｜五个测试位置（评审指定的）

必须在这些位置各抓一张图，**三种模式对比**：

| # | 位置 | 看什么 |
|---|---|---|
| 1 | **开阔道路** | 圆形视野的边缘是否圆滑（最容易看出差异） |
| 2 | **墙角** | 转角处是否还有生硬的直角 |
| 3 | **房门** | 门框形成的窄缝边缘 |
| 4 | **沙发边缘** | 小型遮挡物周围（之前踩过"只亮一半"的坑） |
| 5 | **靠墙摆放的物品** | 物体与墙重叠处 |

⚠️ **第 4、5 项是回归重点**。2026-10-14 修过一次
「贴身家具挡死玩家视野」（沙发只亮一半 / 夹缝完全无视野），
视觉改造**不能把这个 bug 带回来**。

### Step 4｜测帧率

用 Movie Writer 或引擎自带计数器，记录：

| 指标 | 目标 |
|---|---|
| 平均 FPS | ≥ 60（或与现状持平） |
| `_draw()` 单次耗时 | < 2ms |
| 最低 FPS（最低谷值） | 不低于 45 |

⚠️ **如果 FPS 明显下降，第一时间把视觉密度调回 16px 或退回纯色矩形。**
美术友好是优点，但不能牺牲流畅度。

## 六、原型通过后怎么办

原型验证通过后，再决定：

| 结果 | 下一步 |
|---|---|
| 柔化效果好、帧率够 | 全面替换 `_draw()`，去掉调试开关 |
| 效果好但帧率不够 | 降低视觉密度（8px → 12px/16px） |
| 效果一般 | 考虑方案 A（距离场），或保持现状 |
| 边界插值不够用 | 考虑 **Shader 方案**：用一个 `CanvasItem` shader 做距离场平滑 |

**Shader 方案**（备选，本轮不做）：
用 `light_mask` 纹理 + shader 做边缘柔化，由 GPU 完成，
CPU 只负责更新纹理数据。这是最彻底的方案，但要引入 Shader 语言，
对 0 基础项目是个学习成本。

## 七、前置依赖（重要）

**上一批的遮挡修正（`_ray_ends_inside`）应先完成并通过实机验证。**

理由：遮挡修正改变的是「哪些格被点亮」，视觉改造改变的是「怎么画」。
如果同时改，出现问题时无法判断是哪个造成的。

**建议顺序**：
1. 遮挡修正 → 实机验证（能看到车全貌 + 隔墙遮挡没被破坏）
2. 本批视觉原型 → 五位置对比截图 + 测帧率
3. 决定是否全面替换
